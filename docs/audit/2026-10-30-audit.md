# 2026-10-30 — kashi 1.3.0 security & hardening audit (P(-1))

**Scope**: the whole 1.2.2 surface, as the P(-1) pass at the 1.3 minor cut.
The last audit was 2026-05-28 (0.8.0); 1.1.0 and 1.2.0 shipped without one.
The pass re-walks everything the 0.8.0 audit covered. It also covers what
has never been audited:
- 1.1.0's `kashi_cp437_from_unicode` and its reverse index, the extension
  block, and the library face's built-in mapping;
- 1.1.1's right-sized glyph buffers;
- 1.2.2's PCF guard;
- the environment around the code: file paths that are not regular files,
  threads, global names in the published bundle, aarch64, and benchmarks.

**Method**: a multi-agent review run as a workflow (188 agents; all
probes ran in scratch copies, never in the repo):
1. **Find.** Eight auditors, one per surface or lens:
   - the freestanding core;
   - the PSF, BDF and PCF paths;
   - the library face;
   - algorithmic cost, with measurements on in-cap worst-case inputs;
   - a regression re-walk of the 0.8.0 CVE checklist and its F1 – F9;
   - test and fuzz adequacy, by mutation testing.
2. **Verify.** Two independent verifiers for every finding: a
   **reproducer**, which built a probe and ran it (re-measured costs,
   applied mutants), and a **skeptic**, which tried to refute it from the
   code. A finding was kept only if it was reproduced, or neither verifier
   refuted it. Severity is the verifiers'.
3. **Critic.** A completeness critic read every function in `src/`
   against what had been checked and named five cross-cutting gaps:
   - thread safety;
   - non-regular file paths;
   - bundle namespace collisions;
   - aarch64;
   - the benchmark baseline.

   A targeted auditor covered each, with the same verification.

**Result**: 87 raw findings. One was refuted (a CI step that only looked
wrong; it was fixed anyway, T9). The remaining 86 deduplicate to the 34
entries below:
- **1 high:** quadratic map construction, measured at 204 s for one font
  within the caps;
- **5 medium** (L4, L5, L6, L7, B1);
- **the rest low / info.**
- **Exploitability:** nothing is exploitable for code execution. Every
  memory-safety finding needs a forged parser context or a corrupted
  global, never a font file or an accessor argument.

The freestanding core came through clean apart from one
defense-in-depth clamp (C1). 75.8 M accessor checks over the full i64
domain found 0 failures, and the core's reverse index matches Python's
`cp437` codec for all of U+0000 – U+10FFFF.

The test suites were the weak point: **47 of 57 plausible mutants
survived all three suites.** 1.3.0 fixes every finding that is kashi's to
fix, and adds the tests that kill those mutants. What it leaves open is
listed at the end.

## Findings

IDs: **L** library face (`src/lib.cyr`), **B** BDF, **P** PSF, **F** PCF,
**C** core, **T** tests / CI, **D** documentation. Each fixed finding has a
regression test, named under *Verification*.

### L1 — Codepoint maps were insertion-sorted: quadratic in the table · **High** · Fixed

**Problem.** All four map builders sorted their {codepoint, glyph} pairs by
insertion sort: the PSF inline table (`_kashi_build_umap`), the BDF loader,
the PCF loader and the text-table attach. A table in reverse order is the
worst case, and the caps admit very large tables.

**Measured on 1.2.2** (several auditors independently; the reproducer
re-measured each):

| Input (within its cap) | Load / attach time |
|---|---|
| 256 KiB PSF2, ~262k table entries | **204 s** |
| 256 KiB PSF1 | 52 s |
| 256 KiB binary table attach | 204 s |
| 256 KiB text table attach | 22.6 s |
| 65,536 BDF glyphs, descending ENCODING (3.4 MiB) | 13.3 s |
| the same BDF, ascending | 81 ms |

Real kbd console fonts load in 0.17 – 0.65 ms.

**Fix.** One builder, `_kashi_pairs_finish` (ADR 0012):
- an already-sorted input is detected in one pass and left alone;
- anything else is heapsorted, which is O(n log n), in place, with no
  allocation;
- duplicates are then dropped by a fixed rule (L10).

**After** (same inputs and probe):

| Input | Before | After |
|---|---|---|
| PSF2 256 KiB | 204 s | **69 ms** |
| PSF1 | 52 s | **4 ms** |
| binary attach | 204 s | **69 ms** |
| text attach | 22.6 s | **26 ms** |
| BDF 65,536, either order | 13.3 s | **51 ms** |

Typical loads are unchanged (`docs/benchmarks.md`, *Load paths*).

### L2 — `kashi_font_seq_glyph` was a linear scan · Low · Fixed

**Problem.** A font file sets the number of sequence records. With ~130k of
them, every lookup cost 0.70 – 0.85 ms (measured by five auditors).

**Fix.** Records are sorted (lexicographically by codepoints, then length)
and binary-searched. A repeated sequence keeps its highest glyph. With
53,248 distinct sequences a lookup now costs **153 ns**.

### L3 — `*_file` reserved a cap-sized buffer before opening, for good · Low · Fixed

**Problem.** Each `*_file` call allocated its full cap (256 KiB or 4 MiB)
from the bump heap before `open`, and kept it on every outcome. 100 calls
on a missing BDF path held 400 MiB.

**Fix.** `_kashi_read_file` allocates after a successful `fstat`, sized to
the file. A missing path allocates nothing.

### L4 — Over-cap files were cut at the cap and loaded · Medium · Fixed

**Problem.** A PSF over 256 KiB, or a BDF / PCF over 4 MiB, was truncated
and loaded as a partial font with success. For example, an 8.3 MB BDF
declaring 50,000 glyphs loaded 25,332 of them, so the remaining codepoints
silently drew nothing. The docs said "rejected" in places.

**Fix.** A file over its cap is `0 - KASHI_EINVAL`.

### L5 — `*_file` blocked forever on a FIFO / tty; a tty became the controlling terminal · Medium · Fixed (Linux)

**Problem.** The CVE-2017-16611 pattern. All five `*_file` APIs blocked in
`open` on a FIFO with no writer, and in `read` on an idle one (killed at
12 s in every case). A session leader that opened a pty acquired it as its
controlling terminal, and `^C` then killed the loader.

**Fix.** On Linux, `_kashi_read_file`:
- opens `O_NONBLOCK | O_NOCTTY | O_CLOEXEC`;
- fstats the open descriptor (no stat/open race);
- accepts only a regular file.

Every non-regular path returns `0 - KASHI_EINVAL` in about 1 ms. agnos,
Windows and macOS keep the stdlib's blocking read (ADR 0012).

### L6 — A load could succeed with a half-built record · Medium · Fixed

**Problem.** Two ways to register an incomplete record:
- Loaders registered the font and only then built its map, ignoring an
  allocation failure. With `n * 16` over the allocator's limit, a PSF
  "loaded" with no map in 3.5 s.
- `_kashi_rt_register` did not check `vec_new()`, so the first
  registration under OOM dereferenced null.

**Fix.** Maps are built first. The complete record is registered by
`_kashi_rt_register(…, maps)`, and an allocation failure fails the load.
`vec_new` is checked. (`vec_push` itself still aborts on OOM; that is the
stdlib's policy.)

### L7 — A table that mapped no single codepoint fell back to identity · Medium · Fixed

**Problem.** A PSF whose table held only sequences, or a successful attach
of such a table, left `RT_UMAP == 0`. The font was then addressed by raw
glyph index, so U+00E7 'ç' drew 'τ'. Three auditors found this
independently.

**Fix.** Such a font gets the empty map and misses every codepoint. Only a
font with no table at all uses identity addressing.

### L8 — Attach cleared the live map before parsing · Low · Fixed

**Problem.** The F9 rollback restored the old map on failure, but in
between the record was empty. Measured with readers on another thread:
U+0041 resolved wrong in 57 – 70 % of reads during a loop of failing
attaches (5.8 ms window per attach).

**Fix.** Maps are built aside and stored only on success. The record is
never cleared.

### L9 — Text-table codepoints were not range-checked · Low · Fixed

**Problem.** The text attach accepted surrogates and values up to 2^48 − 1,
unlike the binary tables' strict decoder. `SECURITY.md` claimed both
shared that decoder.

**Fix.** A `U+` value above `0x10FFFF` or in `U+D800..U+DFFF` is
`0 - KASHI_EFORMAT`.

### L10 — A duplicated codepoint resolved by accident of map size · Low · Fixed

**Problem.** 85 of 136 surveyed kbd fonts list one codepoint for several
glyphs. Which one the binary search found depended on the map's size:
kashi picked the first 81 times and the last 108 times. The same applied to
duplicate BDF `ENCODING`s.

**Fix.** The highest glyph index wins, the Linux console's rule (ADR 0012).

### L11 — Unprefixed internal names in the published bundle · Low · Fixed in part

**Problem.** `dist/kashi.cyr` exported `_rt_registry` and 68 unprefixed
enum constants. A consumer global named `_rt_registry` silently shared its
storage, and a consumer `RT_SEQDATA` redefinition made attach write past
the record. Neither produced a diagnostic, even under `--strict`.

**Fix.** The internal ones are now `_kashi_rt_registry` and `_KASHI_RT_*`
(enum `_KashiRtRec`, documented as internal layout).

**Open.** The parser struct constants (`BDF_PH_*`, `BDF_CTX_*`, `BG_*`,
`PCF_PH_*`, `PCF_CTX_*` and similar) are documented API, so prefixing them
is a breaking change. Booked on the roadmap.

### L12 — The library face is not thread-safe · Low · Documented, not fixed

**Problem.** Measured on x86_64 and under qemu-aarch64:
- concurrent `kashi_register_font` calls lose fonts and return ids that
  address another caller's font;
- an enumerating reader can trip `vec_get`'s abort while the registry
  grows;
- a reader racing a text attach can binary-search a torn {map, count} pair
  (a heap over-read, caught by a guard-page probe).

**Response.** kashi has no lock primitive in its dependency set, and every
consumer is single-threaded. The contract is now written down in
`docs/api/README.md` *Thread safety*: serialize every registry, loader and
attach call, and do not read a font while attaching to it. L6 and L8
narrow the windows but do not close them.

### L13 — `-EINTR` surfaced as a load failure · Low · Fixed (Linux)

**Problem.** A signal without `SA_RESTART` during a slow read returned
`0 - KASHI_EINVAL`.

**Fix.** The Linux reader retries `-EINTR`.

### L14 — `attach_*_file` opened the path before validating the font id · Low · Fixed

**Problem.** A call that had to fail (built-in or unknown id) still opened
the path, so it could hang on a FIFO and kept 256 KiB.

**Fix.** The id and the kind are checked first.

### B1 — A BDF cut before `ENDFONT` loaded as a partial font · Medium · Fixed

**Problem.** The glyph cursor reports END both at `ENDFONT` and at the end
of the buffer, so a truncated file loaded whatever glyphs preceded the cut.
6.1 % of cut offsets did this silently.

**Fix.** `kashi_load_bdf` requires an `ENDFONT` line
(`_kashi_bdf_has_endfont`). The cursor keeps its partial-buffer semantics
for direct callers.

### B2 — The BDF glyph store was sized from the declared `CHARS` · Low · Fixed

**Problem.** A 401-byte file declaring `CHARS 65536` at 32×32 reserved
9 MiB per load, and kept it on failure. 100 loads reached 315 MB RSS.

**Fix.** The count is bounded by what the input can hold. A glyph record
spends at least 33 bytes on its five keywords, so the bound is
`(len − dataoff) / 33 + 1`.

### B3 — Extra `BITMAP` rows were ignored · Low · Fixed

**Problem.** Rows past the BBX height were silently skipped, while missing
or wider rows were rejected.

**Fix.** After the rows, only `ENDCHAR` may follow.

### B4 — Numbers accepted trailing junk: `ENCODING 0x41` mapped U+0000 · Low · Fixed

**Fix.** `_kashi_bdf_int` requires the number to end at a field boundary.

### B5 — Repeated header keywords: last one wins · Low · Fixed

**Problem.** The 0.8.0 F8 duplicate rule had not been applied to BDF.

**Fix.** A second `STARTFONT`, `FONTBOUNDINGBOX` or `CHARS` is
`KASHI_BDF_EFORMAT`.

### B6 — `kashi_bdf_next_glyph` trusted its ctx · Low · Fixed

**Problem.** A forged ctx could make `fbb_h * stride` wrap past the
`dest_size` check: 4 bytes were written past a 16-byte destination.

**Fix.** The ctx's width and height must lie in 1..32, else
`KASHI_BDF_EINVAL`. A ctx from a failed parse is zeroed and so refused.

### P1 — PSF1 tables accepted surrogate codepoints · Low · Fixed

**Problem.** The PSF2 UTF-8 path has rejected `U+D800..U+DFFF` since the
0.6.0 audit F2; the PSF1 u16 path did not.

**Fix.** A surrogate now ends the PSF1 table (`TOK_END`), as on PSF2.

### P2 — `kashi_psf_uni_token` dereferenced a null `out` / `buf` · Low · Fixed

**Problem.** `kashi_psf_parse` rejects nulls; the token function crashed.

**Fix.** `out == 0` returns without writing, and `buf == 0` reports END.

### F1 — A failed `kashi_pcf_parse_header` left a usable-looking ctx · Low · Fixed

**Problem.** `parse_header` stored the glyph count before validating the
metrics, bitmaps and encodings. On a later failure the ctx kept that count
next to zeroed offsets. `decode_glyph` on it read far past the buffer
(SIGSEGV on a 157-byte input), and `cp_to_idx` read the encodings table.

**Fix.** Every later failure clears the count, and `cp_to_idx` refuses a
ctx with a zero count.

### C1 — The reverse-index search was bounded by a mutable global · Low · Fixed

**Problem.** `kashi_cp437_from_unicode` set `hi = kashi_cp437_n - 1` with no
clamp. It is the only core access bounded by runtime state. Neither a font
nor an argument can reach it, but a corrupted count read foreign bytes
(n = 200) or crashed (n ≥ 0x4000).

**Fix.** `hi` is clamped to the index's 128 slots. That is behaviour-
preserving, verified over every codepoint before init, after init and
after re-init.

### T1 – T9 — Tests and CI · Fixed (T8 open)

- **T1. `fuzz_psf` never accepted a font.** 0 of 4,000 inputs parsed, so
  its post-parse contracts never ran.
- **T2. Fuzz contracts checked ranges, not answers.**
  - This is how the 1.2.2 PCF bug survived from 0.7.1.
  - `fuzz_core` took its oracle from the code under test.
  - `fuzz_bdf` only produced stride-1 glyphs.
- **T3. PCF decoding was tested in exactly one format.** No scan-unit swap,
  big-endian table, glyph pad over 1, width over 8 or multi-row encoding was
  covered. 11 decode mutants survived, one of them a stack OOB write. (The
  auditor's independent X11 reference agreed with kashi on 440 / 440 cases,
  so the code was right; the tests could not have shown it.)
- **T4. Validation boundaries were untested:**
  - the PSF length guards at the exact boundary (6 over-read mutants);
  - the PCF structural guards (7 mutants);
  - the PSF count cap, the overlong boundary and PSF1 mode bit 3;
  - BDF widths other than 8;
  - the reverse-index packer guards (all five removable with every suite
    green);
  - the 0.8.0 F3 regression test, which could not fail.
- **T5. Sorting, ligatures and rollback were barely tested:**
  - the sorts were never fed unsorted input (deleting the PSF sort passed
    everything);
  - ligatures were tested with one sequence;
  - the F9 rollback test used a font without sequences;
  - the first unregistered id was never queried.
- **T6. One heap-overflow mutant was caught only under poison.** A mutant
  in `kashi_load_bdf` passed every plain run and only `CYRIUS_POISON`
  caught it, but CI never built a poisoned run.
- **T7. Integration-suite hygiene:**
  - it used fixed `/tmp` names (concurrent runs raced; 1 in 120 failed);
  - it called raw `syscall(SYS_UNLINK)`, so it did not compile for
    aarch64;
  - `kashi_attach_unicode_table_file` had no test, and no test covered
    non-regular paths.
- **T8. No aarch64 CI leg.** The suites pass under qemu-aarch64 (unit 464,
  integration 145, fuzz, the glyph sheet `5544d63f…`). The leg itself is
  booked on the roadmap.
- **T9. The CI fuzz step called a timeout (exit 124) a pass.** The step
  failed anyway, only because GitHub runs it under `bash -e`. The finding
  was refuted as a live bug, but the step's logic is now explicit.

**Response.** T1 – T7 and T9 are answered by the 1.3.0 test files and CI
steps listed under *Verification*.

### D1 — Documentation

- **SECURITY.md:**
  - it overstated fuzz coverage of the unified accessors;
  - it said the text table shares the strict decoder (L9).
- **The PCF guide** said over-cap files are rejected. That is true from
  1.3.0 (L4).
- **No thread-safety statement** existed (L12).
- **The 0.8.0 checklist** omitted CVE-2017-16611 (added above).
- **Two cost figures in `docs/api/core.md`** described best cases:
  - `kashi_font_init`'s ~21 µs is warm (a first call costs 30 – 38 µs);
  - the ~25 ns high-half lookup is one probe depth (most lookups and every
    miss cost 11 – 30 % more).

## Found clean

Recorded so the next pass need not redo them. Each item was re-checked on
the current code, most with a probe.

- **The freestanding core**:
  - every accessor over the full i64 domain: 75,803,109 checks, 0 failures,
    every returned pointer inside its buffer and every row equal to
    `load8` of it;
  - every byte span against `_KashiFontStore`: the highest access is the
    last byte of each buffer;
  - the packers' and the index writer's guards;
  - the 9×16 derivation bounds;
  - `kashi_font_init` idempotence;
  - the reverse index: sorted, a bijection onto `0x80..0xFF`, equal to
    Python's `cp437` codec for every codepoint;
  - the freestanding boundary (`cyrius vet`: no dependencies).
- **The 0.8.0 F1 – F9**: every fix is still in place and every regression
  test passes.
- **The 0.8.0 checklist, all eight clean items re-confirmed**:
  - `count * size` products are i64 and capped before allocation;
  - every PCF `offset + size` is checked against the file;
  - metric signedness;
  - the bitmap size bound;
  - table-walk termination (`pos` strictly advances);
  - no string-table reads;
  - `load32` sign hygiene;
  - the 65,536 count caps.
- **PCF decoding**: 440 / 440 cases agree with an independent X11
  reference implementation. A 300,000-round guard-page fuzz found 0
  faults.
- **BDF**: 503 truncated prefixes and 36,646 mutants under a guard page
  found 0 faults.
- **Unified and runtime accessors**: 192 M edge-value calls and 20 M random
  64-bit rounds found 0 bad results.
- **Real fonts**: all 136 kbd console fonts load. Attaching their
  `psfgettable` text tables gives the same map as the inline table in every
  case.
- **Namespace**: 0 collisions between kashi's names and the 6.7.18 stdlib or
  any consumer repo (one name, `RT_STRIDE`, collides with one unrelated fuzz
  file elsewhere).
- **aarch64**: unit, integration and fuzz all pass. The glyph sheet and a
  226-entry loader differential are byte-identical to x86_64.

## Open after 1.3.0

| Item | Why open | Where it is tracked |
|---|---|---|
| L11, the parser struct constants | Documented API; prefixing them is a breaking change | Roadmap 1.x.x / 2.0 |
| L12, thread safety | No lock in kashi's dependency set; every consumer is single-threaded | Documented contract |
| L5 on agnos / Windows / macOS | No portable non-blocking open + fstat there | ADR 0012 |
| T8, an aarch64 CI leg | CI change; suites verified under qemu here | Roadmap |

## Verification

Everything below was run on the 1.3.0 tree with cyrius 6.7.18.

- **Gates:**
  - `cyrius build` for x86_64, aarch64, agnos and Windows;
  - `cyrius vet` "no dependencies" on all four freestanding files;
  - `cyrius fmt --check` and `cyrius lint --exit-with-count
    --strict-deferrals` clean on all 15 source files;
  - the glyph sheet still hashes to `5544d63f…`.
- **Suites** (`cyrius test`), all passing, plain and under
  `CYRIUS_POISON=1`. Each finding's regression test is named in its file's
  `test_group`:

  | File | Assertions | What it covers |
  |---|---|---|
  | `src/test.cyr` (unit) | 464 | unchanged |
  | `tests/kashi.tcyr` | 145 | per-process temp names, portable unlink (T7) |
  | `tests/maps.tcyr` | 208 | L1, L2, L6, L7, L8, L9, L10, the registry edges |
  | `tests/parsers.tcyr` | 273 | B1 – B6, P1, P2, F1, C1, the T4 boundaries |
  | `tests/pcf_formats.tcyr` | 92 | T3 (320-font PCF decode matrix against a reference decoder in the test), BDF widths 1 – 32 |
  | `tests/files.tcyr` | 207 | L3, L4, L5, L14 and descriptor hygiene, on all five `*_file` APIs |
  | **Total** | **1,389** | was 609 |

- **Fuzz** (`tests/kashi.fcyr`, T1 / T2), plain and `--poison`:
  - round-trip answer oracles for PSF, BDF, PCF and the text table;
  - `fuzz_core` against an independent cell model;
  - a unified-accessor contract over the full i64 domain;
  - a sort-cost guard.

  `fuzz_psf` accepts 1,627 of its 4,000 inputs (it accepted 0).
- **aarch64**: all six suites pass under qemu-aarch64.
- **Mutation testing**:

  | Mutant set | Killed | Equivalent | Untestable here |
  |---|---|---|---|
  | The audit's 57 (1.2.2's suites killed 11) | 52 | 5 | — |
  | 106 new, aimed at every 1.3.0 fix | 98 | 4 | 4 |

  - **The 5 equivalent audit mutants:** 4 change no observable behaviour; the
    fifth, `LIB-RTCPNEG`, changes nothing visible through the public API.
  - **The 4 untestable here:** they need a session-leader pty (`O_NOCTTY`),
    a timed signal (the `-EINTR` retry) or a racing writer (the "file grew
    while read" check, two mutants). Each fix was verified by reading and by
    the audit's probes.
  - **Two further code defects** turned up while writing tests and are fixed
    in 1.3.0:
    - registry growth under OOM aborted through `vec_push` (now
      `vec_push_a`);
    - a keyword line after the `BITMAP` rows was still parsed (B3, now
      refused).
- **Bench** (nine interleaved rounds against 1.2.2): hot accessors flat
  (±2.4 %); typical loads +1 – 7 %; a 4,096-entry reverse-ordered table
  44.2 ms → 1.10 ms. Full table in `CHANGELOG.md` 1.3.0 and
  `docs/benchmarks.md`.
